strands_evals.optimization

Optimizing a Strands agent's harness

A new Strands Evals module that searches an agent's prompts, tool descriptions, settings and components together, and measures every candidate with repetitions and 95% intervals.

The problem

Fix the model, and an agent's quality and cost still depend on its harness. That covers the system prompt and each tool's description, which conversation manager trims the history and with what settings, whether the model thinks before it acts and on how many tokens, and structural choices such as whether a write to a customer's records is held back and checked again before it runs.

Today we tune these by hand, one change at a time. Someone edits the prompt, runs a few cases once, and compares the averages. With no repetitions and no intervals, a real gain of a few points looks the same as run-to-run noise, and each change is judged against whatever the other settings happened to be that day.

The variables are also of different kinds. A prompt is free text, a window size is an integer, and a conversation manager is a choice between components that each bring settings of their own, settings that exist only when that component is chosen. Optimizers built for numbers and choices, such as Optuna's, cannot write text. Prompt optimizers rewrite text and leave everything else where it was.

Failures also hide in the averages. When the agent raises an exception, a model call is throttled, or a simulated user crashes, the run often scores 0 and goes into the mean with the real answers, so a broken environment reads as a bad prompt.

How a study works

The module turns tuning into a measured search over declared variables. You write an ordinary Strands agent factory and declare its tunable arguments, as Python objects, in a @tunable decorator. A Study builds a fresh agent from the factory for every trial, runs it on a Strands Evals Experiment, and turns the evaluators' scores and the agent's usage into estimates with intervals.

A search proposes each next candidate. Each kind of variable gets a method suited to it, and a schedule decides which methods move in each iteration while the rest of the candidate stays at the best found so far.

What a study measures

Tunable variables
The factory's arguments, declared as objects. TextValue is free text. Int, Float and Choice are settings. OneOf(component(...), ...) is a choice between components that each have their own settings. tool_descriptions(...) makes each tool's description a text, and SkillLibrary makes a library of Agent Skills a value. A search names these same objects.
Candidates and trials
A candidate is one set of values. It runs every case of the experiment repetitions times, and each run is a trial with a status. A trial whose agent raised is an agent_failure, scored by a declared policy (by default the worst end of the metric's range). A trial that measured nothing, because a call was throttled or a simulated user failed, is invalid. It runs again and never enters an average.
Estimates
Repetitions are averaged within each case and the case is the unit, so every metric is a mean over cases with a 95% interval.
Objectives
Maximize and Minimize name a metric. It can be an evaluator's score, the agent's usage (tokens, seconds, model_calls, removed_messages), or a Derived metric computed from those for each trial. Several objectives are wrapped in how they combine. Pareto keeps the front; WeightedSum, Chebyshev and Lexicographic rank candidates by one number or one order; Independent gives each objective its own copy of every method.
Constraints
AtLeast and AtMost put a limit on any metric, a Derived one included. A candidate that breaks a limit is infeasible and is never the best.

How it searches

Blocks
A block is a method and the variables it proposes. TPE, Optuna's tree-structured Parzen estimator, proposes numbers and choices. Reflection gives a stronger model (Claude Sonnet 4 by default) the held candidate's trials, those that scored well beside those that did not, and the model rewrites the texts the traces give it a reason to change. SkillCuration creates, revises or retires the skills in a library. A variable that no block names goes to the default block for its kind.
Schedules
A schedule says which blocks move in each iteration; the others stay at the incumbent. Joint() moves every block every time, and Alternate(...) one block at a time. Nested(outer=..., inner=...) runs rounds. The outer block proposes (a conversation manager, say), a short inner search runs under that choice, and the outer method is told the round's best. Schedules nest to any depth.
No repeats
Values already measured are never measured again. A step that repeats a measured candidate tells its methods that candidate's result and proposes again, up to redraws times. If it still repeats, the schedule moves on.

Together this is block-coordinate optimization. Each block proposes its own variables from the same held candidate, and every block's method learns from the same results.

What it records

With record=, the study appends each candidate to study.jsonl as it finishes. The entry holds the candidate's values, what each method proposed and was told, its trials and their transcripts, its estimates and constraint violations, and its place in the schedule. The explorer in explorer/ reads that file and draws only what it records. The panels on this page are the explorer, opened on each study's record.

TPE proposes, but it keeps no posterior over outcomes and ignores measurement noise, so the candidates it picked say little about which options helped. After each run, effects.py fits BayesBench, a conjugate Gaussian model of main effects and two-way interactions, to the record. Its factors are the choices at any depth, each number binned into three ranges of the values tried, each text by how many rewrites deep it is, and the case, so that a hard case is not mistaken for a bad option. For each option and goal it reports the effect in the goal's own units with a 90% credible interval, along with diagnostics that say whether the model fits well enough to read. The explorer shows these on its Overview and Search space pages. BayesBench is installed separately; without it, a run writes no effects.

Hello world: poems of 40 to 60 words

The smallest study tunes one text. The poet's system prompt starts as “You write poems about the topic you are given.” The evaluator passes a poem of 40 to 60 words. Six topics, each run twice, give 12 trials per candidate, and the objective is to maximize WordCount, the share of poems that pass. In the listings, names from strands_evals.optimization are set in blue. This study uses four of them.

The study is given no search, so the system prompt goes to the default block for text, contrastive reflection. This TextValue has no max_chars, so reflection appends what it learned to the prompt; a text with a limit, such as a tool's description, is rewritten within it. study.optimize(iterations=4) measures the baseline (the agent at its defaults) and then up to four rewrites.

Reflection's agent runs shell commands over the trial transcripts, so run the example where model-written shell commands are acceptable, such as a devbox or a container. It calls Amazon Bedrock, so it also needs AWS credentials and model access. From the repository root:

BYPASS_TOOL_CONSENT=true python examples/optimization/poem_length.py

The document reader

The second study searches every kind of variable at once. The agent, Claude Haiku 4.5 with a 4,000-token context limit, must read a synthetic document page by page. Each of the ten pages buries one digit of a code in filler text, along with the key that unlocks the next page, so the pages can only be read in order. At the end the agent replies with the ticket id from its request and the whole code. The reply earns one point for the ticket id and one for each digit in its place, out of 11.

Whether it can do that depends on what its conversation manager keeps. The sliding window keeps the last window_size messages, and reading ten pages takes at least twenty; pinning the first message keeps the request, and its ticket id, in view. The summarizing manager replaces the oldest messages with a summary once the conversation fills 60% of the context window, and a summary can drop a digit.

The study rewrites the system prompt and both tools' descriptions by reflection, and uses TPE to choose the manager and tune each manager's settings. It runs in rounds (Nested). Each round proposes a manager, then searches the texts and that manager's settings jointly for four iterations under it. There are two objectives, a higher answer score and fewer tokens, kept as a Pareto front, and two limits: an answer score of at least 0.8, and at most 30,000 tokens per trial on average. Three documents, each run twice, give six trials per candidate.

With iterations=10 after the baseline, the schedule runs two rounds of five candidates: each round's opening candidate, which proposes the manager, then four joint steps under it. The full file comments every argument with its default and the alternatives, and document_reader_steps.py builds the same study in six steps, one idea at a time.

Results

τ²-bench airline

τ²-bench, from Sierra Research, puts a customer-service agent in a conversation with a simulated customer who has a goal, under an airline's written policy and with 14 tools for looking up and changing reservations. Here the agent is Claude Haiku 4.5, a deliberately weak model for this benchmark, and the simulated customer is Claude Sonnet 4.6 for every candidate. Each case is one of τ²'s airline tasks. τ² runs the whole conversation, executes every tool call the agent makes, and scores the result. The reward is 1 when the airline's database ends as the task requires and the agent told the customer what it had to, and 0 otherwise.

The study rewrites the agent's instructions and the descriptions of all 14 tools by reflection, and tunes its thinking budget by TPE, from 0 to 16,384 tokens per model call in steps of 1,024. The airline's policy is part of the benchmark and is never tuned; the instructions come before it in the system prompt. The baseline is τ²'s own agent, with its instruction, temperature 0, no thinking, and the tools' own descriptions. The search runs on 10 of τ²'s airline train tasks, one repetition each. Afterwards the baseline and the best candidate run again on 10 of τ²'s test tasks, twice each. The search never saw those tasks.

A trial is a whole conversation

By default a study's task calls the agent once on the case's input. A τ² trial is a conversation of many turns that τ² drives, so the study takes task=Tau2Task("airline"), a callable that receives the agent built for the trial and the case, and returns the output the evaluators score. τ² has to execute every tool call itself, because its evaluator replays those calls against a fresh database. A hook interrupts each call the agent makes, τ² executes it, and τ²'s result resumes the agent.

Some conversations fail for reasons outside the agent. The simulated user's model call errors, or τ² ends the conversation with a user or infrastructure error. For those the task raises TrialInvalid. The study records the trial as infrastructure_invalid and runs it again (retries=2 by default); if every attempt fails, the trial stays invalid and no average includes it.

What's next

Picking winners needs more care. The best candidate's search score is the highest of many noisy estimates, so it overstates how that candidate does on tasks it was not chosen on. In six of the eight τ²-bench studies run so far with tau2_airline_steps.py, the best candidate scored lower on the held-out tasks than in the search. More tasks and repetitions per candidate narrow the intervals. A held-out selection split would choose among the leading candidates on cases the search never saw, and leave a third set for the score we report.

Today each block's method proposes its own variables from the same held candidate, and the methods learn from the same results but not from each other's proposals. A joint model-based step is planned to change that. It fits one surrogate over numbers, choices and features of the texts (their rewrite lineage, the rules they contain), with interactions. Reflection would write several text edits in one call, sampling would propose numbers and choices, and Thompson sampling or expected improvement would pick a combination. When the surrogate's diagnostics flag a poor fit, the step falls back to the coordinate search.

Packaged benchmarks will come through Harbor. With Strands Evals' Harbor integration, still pending, a candidate becomes one run of a packaged benchmark, each of Harbor's task results becomes a trial, and the agent acts in the task's container. A version of the document reader with each document as a packaged task comes with that integration, and ContextBench and τ² banking are the next workloads planned on it.
